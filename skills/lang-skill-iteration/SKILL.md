# Skill Iteration

把真实工作中的“这次为什么这样改”，转化成 AI 下次能够执行、又不会过度泛化的规则。

本 Skill 是反馈学习编排层：负责收集证据、解释判断、决定迁移范围和验证结果。实际创建或修改 Skill 时，应继续调用当前环境中的 Skill 创建、测试和发布能力，不复制它们的工程实现。

## 开始前

优先恢复完整证据包：

```text
原始目标
→ 来源与约束
→ AI 版本
→ 用户修改版
→ 实际采用版
→ 数据、反馈或运行结果
```

最少需要“原始目标 + AI 版本 + 用户修改版”。如果当前会话、本地版本或发布链接可以恢复证据，就直接查找；只有缺失会改变判断时才询问用户。

不要只看最终稿，也不要只看机械 diff。用户的改动可能同时包含更好的判断、个人偏好、临时状态、发布妥协和新的错误。

## 六步流程

### 1. 还原任务边界

先确定：

- 产物类型和接收者
- 接收者需要采取的行动
- 原始主目标
- 信息白名单与红线
- 承诺权限
- 事实和版本的权威源

### 2. 建立修改证据账本

只记录有实质意义的变化：

| 原来怎么做 | 用户怎么改 | 变化维度 | 直接证据 | 初步推断 |
|---|---|---|---|---|

变化维度包括：事实纠错、目标与优先级、推理判断、结构与流程、表达与风格、业务配置、交付边界、执行机制。格式和标点可合并说明，避免淹没真正判断。

### 3. 解释为什么

对每项关键改动完成一条因果链：

```text
原写法造成什么理解或执行后果
→ 用户的改法改变了哪个变量
→ 为什么更符合本次目标
→ 换一个场景是否仍成立
```

不要停在“更真实、更有力、更简洁”这类形容词。继续追到可执行判断，例如：“先提供可定位证据，再上升为观点”；或者“决策者先看结论，执行者仍需保留细则”。

### 4. 判断迁移范围

| 级别 | 含义 | 默认落点 |
|---|---|---|
| L0 | 本次事实或一次性修正 | 原项目、事实源或复盘 |
| L1 | 当前项目、客户或渠道配置 | 项目配置或专属 reference |
| L2 | 某个用户或某类产物的稳定偏好 | 私人配置或领域 reference |
| L3 | 跨任务稳定流程 | 目标 Skill 的 `SKILL.md` |
| L4 | 跨所有协作的全局原则 | 先形成充分证据，再由用户明确授权 |

置信度分为高、中、低：用户明确解释或多次重复且有结果验证为高；一次明确修改但未跨案例验证为中；只根据最终版推断为低。

采用只证明“这次选择了它”，发布只证明“被使用”，都不自动证明效果更好。

### 5. 选择权威落点并实施

| 发现 | 应落位置 |
|---|---|
| 单次事实变化 | 事实权威源或项目复盘 |
| 易变身份、产品、字段、目录 | `references/`、配置或最近目录规则 |
| 跨场景稳定判断顺序 | `SKILL.md` |
| 原始失败及其泛化 | `evals/evals.json` |
| 纯表达偏好 | 文风或个人配置 |
| 交付信息边界 | 领域 reference；跨领域升级需明确授权 |
| 尚无效果数据的写法 | 待验证规律 |

修改前检查已有 Skill 能否覆盖，稳定逻辑与易变配置是否分开，是否会覆盖无关改动，以及新规则是否只适配当前案例。

### 6. 验证并交付

重要迭代至少检查：

1. 原始失败场景
2. 相邻泛化场景
3. 反例或例外场景

同时验证文件结构、规则边界和真实行为，留下当前项目要求的 changelog 或测试记录。

## 冲突处理

先判断反馈是否只是条件不同。例如“给老板的回复短”和“内部方法论报告密实”并不冲突，它们对应不同接收者和任务。把表面的绝对规则改写为条件规则。

只有两个反馈在同一对象、目标和条件下仍然冲突，而且选择会改变长期行为时，才请用户裁决。

## 禁止事项

- 不把用户的所有修改都解释成更优。
- 不把最终发布版当成事实权威源。
- 不因一次删短、扩写或改标题生成全局绝对规则。
- 不把私人身份、客户信息、内部路径和业务配置写进公共核心。
- 不以一次通过代替回归测试。
- 不在内部增强层复制本 Skill 全文；内部层只添加自己的配置和规则。

## 输出格式

```markdown
## 核心结论

[最重要的 1—3 个判断]

## 为什么这么改

| 关键变化 | 背后的判断 | 迁移范围 | 置信度 |

## 已经学到了哪里

- SKILL.md：...
- references：...
- evals：...

## 没有学习的内容

- [一次性事实、未经验证推断或潜在错误]

## 验证结果

[检查数、场景数、风险和未解决问题]
```

分析与改动应保存到目标项目的权威位置。先讲真正学到的判断，再讲文件和技术动作。

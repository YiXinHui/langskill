# 通用朋友圈写作

把用户已经提供或明确选择的真实材料，转成一条能继续编辑的朋友圈草稿。核心不是“像谁”，而是让关键事实有来源、表达像用户本人、用户知道稿子依据了什么。

## 职责边界

这是一个公共写作核心，负责：

- 从 1—3 份来源中提取可写事实与主线；
- 结合可选写作画像调整语气、节奏和结构；
- 生成一条主草稿，并给出可核对的来源；
- 在来源不足时收窄结论或明确缺口。

它不负责：

- 扫描私人目录、客户档案或素材库；
- 规划一天 4—5 条内容、安排发布时间或匹配配图；
- 自动发布朋友圈；
- 在用户未确认时从最终修改稿学习写作画像；
- 把狼格拉底或任何特定人物的表达设为所有人的默认风格。

用户明确要求“狼格拉底每日朋友圈规划”“狼哥今天发什么”或同类专属日更编排时，立即停止通用单条写作，简短转交 `lang-wechat-pyq`。当前环境不能调用该 Skill 时，只说明需要专属规划能力；不要扫描目录、搜索素材、加载专属规则链或退化为假装完成整日规划。

## 输入

优先使用产品或用户明确给出的 1—3 份来源。每份来源至少应有可区分的 ID 或标题与正文。`source.title` 只用于识别、选择和展示来源，不能独立支撑草稿或 citation claim 中的事实；事实证据只来自对应 `source.content`。写作画像是可选输入，只能改变表达，不能改变事实。

来源已经以内联文字或产品结构化数据给出时，只处理本轮输入，不调用网络、Shell 或文件搜索去“补素材”。只有用户明确给出本地文件路径且要求读取时，才读取该文件；不能把运行环境中的其他文件当作默认来源。

如果来源超过 3 份，先让用户选择主材料，或只选与当前主张最相关的 3 份。如果没有真实来源但用户只想表达个人感受，可以生成明确标注为“基于用户本轮表述”的草稿；不能补造案例、数据或他人原话。

产品适配器要求结构化输出时，完整读取 [产品输出协议](references/wechat-draft-v1.md) 并严格返回 `wechat-draft-v1`。普通对话中可以使用便于阅读的等价结构。

## 写作流程

### 1. 建立证据边界

先区分三类内容：

- 来源中明确出现的事实、数字、时间、人物和直接引语；
- 用户本轮明确给出的态度、目标和表达偏好；
- 只能推测、不能直接确认的内容。

第三类不能被写成确定事实。对关键结论找不到依据时，删除、降级为疑问或写入警告，不用“合理发挥”补齐。

以下两类扩写同样属于无依据事实：

- 来源没有时间锚点时，添加“今天”“最近”“这几天”“刚刚”等日期或新近性；
- 把“做过访谈”“完成一次梳理”等动作，升级成“摸清整个流程”“找到了根因”“验证有效”“取得阶段成果”等更强结论。

来源中出现一项动作，也不能自动补成另一项过程动作、对象或结果。例如但不限于：从“做了访谈”“查看了资料”推断已经“记录了问题”“识别了痛点”“梳理了流程”或“明确了方向”。分别核对动作、动作对象和完成程度；来源只支持哪一步，就只写哪一步。这些词不是禁止词，来源明确写出相应动作时可以忠实使用。

可以做简单算术推导，但必须能从来源中的数字直接复算，并在措辞中保留“按此计算”“约”等推导边界。

### 2. 选择一条主线

一条朋友圈只推进一个中心判断。优先选择来源之间共同支撑、与用户目标相关、无需额外编造就能讲清楚的主线。

来源之间冲突时保留冲突，不把它们强行拼成共识。材料只是背景但不足以支持结论时，先指出缺口。

### 3. 应用写作画像

画像可以约束：

- 面向谁写；
- 常用句长、节奏和段落密度；
- 倾向的开头与收尾方式；
- 不希望出现的腔调、套话和营销感。

画像不能要求伪造经历、身份、成交结果、用户评价或权威背书。画像与来源冲突时，来源优先。

### 4. 生成主草稿

直接给一条完成度高的主稿，不用用多个平庸版本逃避判断。草稿应做到：

- 开头尽快进入真实场景、问题或判断；
- 正文只使用来源能够支撑的细节；
- 语气自然，避免“在这个时代”“值得我们深思”等空泛开场；
- 若有行动邀请，把它写成与正文一致的自然下一步；
- 不自动添加来源没有出现的时间锚点、数字、人物、机构、结果、阶段判断和引语。

### 5. 做事实审计

逐句核对草稿里的事实性分句。每个事实性分句要么能指向 `source.content` 中的具体证据，要么来自用户本轮明确陈述；连接句和个人判断不能暗中夹带新的时间、范围、因果、阶段或结果。标题即使包含正文没有的动作、范围或限定词，也只能帮助识别来源，不能补充事实。例如（示例，不是穷举或硬编码白名单）：标题写“售后工单抽样”，正文只写“查看了 10 份工单”时，只能写“查看了 10 份”，不能写成“抽样查看了 10 份”。否则修改或删除。

引用的 `claim` 可以是忠实概括，但其中每个事实性动作、对象、数量、时间、范围、程度、关系和限定词都必须由同一条 `excerpt` 支撑，不能再借 `source.title` 补足。`excerpt` 必须是对应来源正文中的连续、完全一致子串，保留原有空格、标点和文字，不能改写、规范化，也不能用省略号或新标点拼接不连续片段。输出前逐项确认 `source.content.includes(excerpt)` 为真，并复核 `claim` 没有超出该片段。一个判断若需要多处不连续证据，拆成多条 citation，让每条 `excerpt` 只引用一段连续原文，并相应收窄各自的 `claim`。来源被移除后重新生成时，不能继续沿用只由该来源支撑的事实。

## 普通对话输出

按最小可用结构输出：

```markdown
## 草稿

[一条可编辑的朋友圈正文]

## 来源

- [来源 ID 或标题]：支撑了哪些关键事实

## 待确认

- [只有确实存在缺口时才出现]
```

没有待确认项时省略该段。不要输出隐藏推理过程，只呈现用户核对事实所需的来源关系。

## 反馈与学习边界

用户编辑、复制、采用或不采用草稿时，可以记录反馈；只有用户明确确认“用最终修改稿更新我的写作画像”时，才把它作为画像学习样本。一次修改只形成候选规律，不能直接变成所有场景的永久规则。

# 滴答推送与回读

只管执行台「每日待办」与滴答（国内版）之间的往返。年、月、周都不推。清单名到 ID 的对照、时区、🐸 的优先级写在 `personal-config.md` 的「滴答推送」一节。

## 分工

- 执行台决定推什么：只有用户确认写入的每日待办才推，不定时、不批量补推历史。
- 状态在滴答里操作：完成、放弃、延期都由用户在滴答做。Agent 不把执行台的状态推到滴答，也不勾选、放弃、删除滴答任务。
- 滴答状态只回读：读回结果作为收口草案的证据，用户确认后才改执行台。

## 推送（每日待办写入并回读之后）

1. 对本次新建、或标题／日期／清单被用户改过的待办，组装 payload：

   ```json
   {"project_id": "<兜底清单ID>", "time_zone": "<滴答时区>", "items": [
     {"record_id": "rec…", "title": "🐸待办原文", "date": "YYYY-MM-DD", "project_id": "<该待办的清单ID>",
      "priority": 5, "content": "周目标：… · 月目标：…",
      "subtasks": [{"title": "第一步"}, {"title": "第二步", "subtasks": [{"title": "2.1"}]}],
      "dida_task_id": "", "old_title": "", "fields": []}
   ]}
   ```

   - **清单**：沿「关联周目标 → 关联月目标」（一次性的事直接用「关联月目标」）找到月目标，按它的「滴答清单」字段，用私有配置的对照表换成清单 ID；选「不推」的不推。月目标的「滴答清单」空着就先问用户，不推到收集箱。
   - **标题**：和执行台一致。挂在 🐸 月目标下的待办，执行台和滴答的标题最前面都有「🐸」，同时按私有配置设 `priority`；其余为 0。
   - **子任务**：能拆才拆，每层最多 3 个，最多两层；只有一层时写成滴答的检查事项，有第二层时第一层建成子任务、第二层是它的检查事项。子任务随日计划草案一起给用户确认，只写进滴答。
   - `content` 写所属周目标、月目标的名字，不写执行台以外的私人信息。
   - 已有「滴答任务ID」的：填 `dida_task_id`，`fields` 只列这次确认改动的字段（`title`／`date`／`priority`／`content`／`project`／`subtasks`）；改了标题的同时填 `old_title`，便于找回被移走的任务。滴答里已有检查事项或子任务的不覆盖。不要因为执行台和滴答日期不同就推日期，那多半是用户在滴答里延期了。
2. 在装了并登录 `dida` 的机器上执行 `python3 scripts/dida_sync.py push`（stdin 传 payload）。跨机调用时把 payload 经 SSH 的 stdin 传过去，不落地含正文的临时文件。
3. 按结果处理：

   | result | 含义 | 下一步 |
   |---|---|---|
   | `created` | 新建并回读一致 | 把 `dida_task_id` 写回「滴答任务ID」并回读 |
   | `matched` | 目标清单里已有同标题、同日期任务（多半是上次建了没回填） | 不新建，直接回填这个 ID |
   | `updated`／`exists` | 已按 ID 更新或无需改 | 无 |
   | `missing`／`deleted` | 原任务找不到或已删除 | 报告，问用户要不要重建；重建时清空旧 ID 后再推 |
   | `readback_mismatch`／`error` | 写了但回读对不上，或调用失败 | 报告部分完成，不重复新建；修好后按 ID 重推 |

   结果里有 `notes`（如「已有子任务，未覆盖」）时照实汇报；`child_task_ids` 是第二层子任务建成的滴答子任务，只汇报不回填。

4. 汇报：推了几条、各自的滴答状态、回填是否回读通过。没有单任务网页链接时给滴答网页入口和清单名。

## 回读（今天收口；做「今天做什么」前顺带核对之前没结的）

1. 取执行台里已填「滴答任务ID」、状态仍是「未开始」「进行中」的待办，组装 `{"project_id", "time_zone", "items": [{"record_id", "dida_task_id", "title", "date"}]}`，执行 `python3 scripts/dida_sync.py read`。
2. 把结果翻成收口草案，每条写明依据：

   | 滴答回读 | 草案建议 |
   |---|---|
   | `status=2` | 状态改「已完成」，注明完成日期 |
   | `status=-1` | 状态改「取消」 |
   | `status=0` 且 `date_changed` | 用户在滴答延期了：日期改成 `due_date`，状态不变；新日期那天按 333 重新核对 |
   | `status=0` 且日期没变 | 未勾不等于没做，问用户（`checklist_done`／`checklist_total` 可作参考）；周期已过且用户确认没做才改「未完成」 |
   | `title_changed` | 列出滴答里的新标题，问是否同步到执行台 |
   | `deleted`／`found=false` | 报告，问用户怎么处理；不清空 ID、不改状态 |
   | `moved` | 记下新清单，照常回读，不移回去 |

3. 用户确认后再写执行台，写完回读。勾选只说明「标过完成」，不等于业务成果；周、月的实际结果仍按复盘方法写。

## 验收

- 只有确认写入的待办出现在滴答，且一条待办只对应一个滴答任务；重复推送不新建。
- 「滴答任务ID」回填后回读一致；回读结果改动执行台前都经过用户确认。
- 调用失败、部分成功、找不到的任务都单列汇报，不说整体完成。

# 滴答推送与回读

只管执行台「每日待办」与滴答（国内版）之间的往返。年、月、周都不推。清单名到 ID 的对照、时区、🐸 的优先级写在 `personal-config.md` 的「滴答推送」一节。

已交专项模块维护的行动先按 [模块交接](module-handoff.md) 核验实际推送结果，个人逐项引用沿用模块的原滴答任务，不重复新建。模块归属已改变时，不能继续沿用混合月目标的旧默认清单。

「来源记录」非空的引用行先走模块单向同步，从下面的个人推送、状态回写、关单和过期改期 payload 中排除；其已有滴答 ID 可以纳入 `known_ids`，避免被误当成未登记任务。要修改工作任务时由负责模块处理原记录和原滴答，再刷新个人引用。

## 分工

- 执行台决定推什么：只有用户确认写入的每日待办才推，不定时、不批量补推历史。
- 状态默认在滴答里操作：完成、放弃、延期由用户在滴答做。Agent 只在用户对某几条回了「行」之后，用 `close` 勾完成或放弃、用 `push` 改日期（见下文「过期没勾」，狼哥 10-09 定）；不把执行台的状态自动推到滴答，不删除滴答任务。
- 执行台的状态由 Skill 从滴答同步（狼哥 10-07 定，取代 10-05「确认后才改」）：用户在滴答里已经操作过的，不再逐条问；只有证据对不上才问。

## 推送（每日待办写入并回读之后）

1. 对本次新建、或标题／日期／时间／清单被用户改过的待办，组装 payload：

   ```json
   {"project_id": "<兜底清单ID>", "time_zone": "<滴答时区>", "items": [
     {"record_id": "rec…", "title": "🐸待办原文", "date": "YYYY-MM-DD", "time": null, "end_time": null, "project_id": "<该待办的清单ID>",
      "priority": 5, "content": "周计划：… · 月目标：…",
      "subtasks": [{"title": "第一步"}, {"title": "第二步", "subtasks": [{"title": "2.1"}]}],
      "dida_task_id": "", "old_title": "", "fields": []}
   ]}
   ```

   - **清单**：沿「关联周计划 → 关联月目标」（一次性的事直接用「关联月目标」）找到月目标，按它的「滴答清单」字段，用私有配置的对照表换成清单 ID；选「不推」的不推。月目标的「滴答清单」空着就先问用户，不推到收集箱。
   - **标题**：和执行台一致。标题带「🐸」的待办（挂在 🐸 月目标下的，或当天按日清单选成 🐸 的），执行台和滴答的标题最前面都有「🐸」，同时按私有配置设 `priority`；其余为 0。
   - **时间**：「时间」非空时转为完整 datetime 的 `time`（`YYYY-MM-DDTHH:mm[:ss][+08:00]`；也接受空格分隔，无 offset 时用 payload 的 `time_zone`）。`date` 必须是开始时刻在该时区的日期；有已确认结束时间就填 `end_time`，且必须晚于开始，跨日写完整结束日期。脚本不加 `--all-day`，`startDate` 为开始、`dueDate` 为结束；只有时间点时两者相同。全天待办 `time`／`end_time` 留空，继续加 `--all-day` 并把两端设为当天零点。不能凭估时补结束；结束信息从模块原记录或本次确认的时段取，个人表只记录开始「时间」。
   - **子任务**：能拆才拆，每层最多 3 个，最多两层；按做的先后排，每条一个动作（脚本按这个顺序设排序值，滴答里照此显示）。只有一层时写成滴答的检查事项，有第二层时第一层建成子任务、第二层是它的检查事项。子任务随日计划草案一起给用户确认，只写进滴答。
   - **长期任务的一步**（规则见 [日清单](daily-plan.md)「长期任务」）：新建时填 `parent_dida_task_id`（主任务的滴答任务ID）和 `parent_title`（主任务原名），脚本把它建成主任务下的子任务，放在已有子任务之后；主任务的标题、日期、状态都不动。这一步下面只能再挂一层检查事项；主任务同时开着的子任务最多 3 个。`dida_task_id` 不能填主任务的 ID，脚本会直接报错、不写。
   - `content`：按 [日清单](daily-plan.md) 第 5 步的分档只补缺的那块（交付物、第一步、定了在哪说），一看就会的可以不写；末尾写所属周计划、月目标的名字。不写执行台以外的私人信息。
     - 分块排版，不堆成一段：「## 做什么」「## 打开」「## 做完以后」等各用小标题，只写用得上的块；一块里有多项就用「- 」列表。
     - 编号不带「#」：写「教程 11」，不写「#11」。滴答会把「#」后紧跟的文字当成标签（10-26 一条描述里的「#11、#43、#68」被建成了三个标签）。标题、描述和子任务里出现「#」紧跟文字的，脚本报错不写；小标题「## 」（# 后有空格）和链接里的锚点放行；「C#语言」这类词中间的 # 也会被拦，改成「C# 语言」或换种说法。
   - 已有「滴答任务ID」的：填 `dida_task_id`，`fields` 只列这次确认改动的字段（`title`／`date`／`time`／`end_time`／`priority`／`content`／`project`／`subtasks`）；改了标题的同时填 `old_title`，便于找回被移走的任务。改日期或时段时，payload 必须带完整确认后的 `date`、`time`、`end_time`（移除时间填 null），脚本同时更新两端并核验 `isAllDay` 和具体时刻；回读仍是全天或时刻不同就报错，不宣称成功。滴答里已有检查事项或子任务的不覆盖。不要因为执行台和滴答日期不同就推日期，那多半是用户在滴答里延期了。
2. 在装了并登录 `dida` 的机器上执行 `python3 scripts/dida_sync.py push`（stdin 传 payload）。跨机调用时把 payload 经 SSH 的 stdin 传过去，不落地含正文的临时文件。
3. 按结果处理：

   | result | 含义 | 下一步 |
   |---|---|---|
   | `created` | 新建并回读一致 | 把 `dida_task_id` 写回「滴答任务ID」并回读 |
   | `matched` | 目标清单里已有同标题、同日期任务，定时任务的时刻及全天标记也一致 | 不新建，直接回填这个 ID |
   | `schedule_conflict` | 同标题、同日期任务的时刻或全天标记不同 | 报告冲突，不新建、不覆盖；核实后按已有 ID 更新 |
   | `updated`／`exists` | 已按 ID 更新或无需改 | 无 |
   | `missing`／`deleted` | 原任务找不到或已删除 | 报告，问用户要不要重建；重建时清空旧 ID 后再推 |
   | `readback_mismatch`／`error` | 写了但回读对不上，或调用失败 | 报告部分完成，不重复新建；修好后按 ID 重推 |
   | `parent_missing`／`parent_deleted`／`parent_closed` | 长期任务的主任务找不到、已删除或已经关了 | 不写；报告并问用户。主任务被误关的，不由脚本重开 |
   | `too_many_steps` | 主任务下已有 3 个没做完的子任务 | 不写；这一步先记成主任务的「下一步」，或请用户先结掉一个 |

   结果里有 `notes`（如「已有子任务，未覆盖」）时照实汇报；`child_task_ids` 是第二层子任务建成的滴答子任务，只汇报不回填。

4. 汇报：推了几条、各自的滴答状态、回填是否回读通过。没有单任务网页链接时给滴答网页入口和清单名。

## 回读与同步（今天收口；做「今天做什么」前顺带核对之前没结的）

1. 取执行台里已填「滴答任务ID」、状态仍是「未开始」「进行中」的待办，组装 `{"project_id", "time_zone", "items": [{"record_id", "dida_task_id", "title", "date", "time", "end_time"}]}`，执行 `python3 scripts/dida_sync.py read`。
2. 按下表直接写执行台，写完回读，再把改了什么一次性汇报给用户：

   | 滴答回读 | 执行台怎么改 |
   |---|---|
   | `status=2` | 改「已完成」，注明完成日期 |
   | `status=-1` | 改「取消」 |
   | `status=0` 且 `date_changed` | 用户在滴答延期了：日期改成 `start_date`（全天等于 `due_date`），并按回读同步「时间」，状态不变；计入新日期的名额 |
   | `status=0` 且 `time_changed` | 同日改时刻、时段或全天转换：同步「时间」为 `time`（全天为 null），结束以回读 `end_time` 为准；跨午夜按 `start_date` 归日 |
   | `status=0`、日期没变、当天已过 | 先不改，按下文「过期没勾」给去向，用户回「行」后再改 |
   | `status=0`、日期没变、还没过完 | 不改 |
   | `title_changed` | 不改执行台标题，汇报里列出新标题，问是否同步 |
   | `deleted`／`found=false` | 不改，汇报并问用户怎么处理；不清空 ID |
   | `moved` | 照常同步状态，记下新清单，不移回去 |

   产出类待办（大纲、方案、文档）以交付物为准：滴答勾了但找不到交付物，或只有 flomo 里的思考，要在汇报里指出，不当作完成。
3. **顺带检查上级**：长期任务的一步（子任务）勾了，只改当天那条日待办，不把主任务标完成；主任务只在全部步骤做完、完成标准达到时才关。待办状态变了，看它的周计划、月目标（一次性的事看「关联月目标」）。完成标准有证据且明确达到的，直接改「已完成」并写实际结果；只做了一部分的，在汇报里列出进度，不改状态。
4. **找滴答里自己加的任务**：把私有配置里的推送清单和收集箱交给 `python3 scripts/dida_sync.py untracked`（`{"project_ids": [...], "time_zone", "from", "to", "known_ids": [执行台里所有滴答任务ID]}`，窗口取上次收口到今天），拿到用户自己加、执行台不认识的未完成任务。逐条按 [目标拆解](planning.md) 的「插入判断」给建议：属于某个月目标的进执行台；杂事留在原清单设截止或取消；想法留在所属项目的清单、不设日期（「将来也许」只放个人生活类想法）。用户拍板后才写入或推送。

### 过期没勾

日期已过、滴答没勾的待办，在早上排计划时（只做复盘时就在复盘里）逐条给一个推荐去向，和草案一起交给用户。用户回「行」，或对某几条回「行」，Agent 才两边一起改；执行台和滴答都改同一条记录、同一个滴答任务，不新建。没回之前两边都不动。

| 去向 | 默认什么时候选 | 执行台 | 滴答 |
|---|---|---|---|
| 挪到今天 | 所挂的周计划本周还要它，今天名额装得下 | 改日期，计入今天名额 | `push`，`fields` 含 `date`；时段变化加 `time`／`end_time`，带完整确认后的时段 |
| 挪到某天 | 本周还要它，但今天装不下：挪到本周名额有空的那天 | 同上 | 同上 |
| 不做了 | 前提变了、被别的事替代，或已不挂在本周计划上 | 改「取消」 | `close`，`action` 为 `abandon` |
| 做了没勾 | 先按 [取证](sources.md) 查，找得到交付物 | 改「已完成」 | `close`，`action` 为 `complete` |

- 「做了没勾」只凭证据推荐，交付物对不上（比如只有 flomo 里的思考）就不推荐这一项。
- 挪过的写进前一天日复盘的「偏差与原因」，执行台不另留一条「未完成」。
- `close` 的输入：`{"project_id", "time_zone", "items": [{"record_id", "dida_task_id", "title", "action"}]}`。结果为 `completed`／`abandoned` 时按上表改执行台并回读；`exists` 是已经是目标状态；`conflict` 是用户已在滴答里关了另一种状态，按滴答为准同步，不翻转；父任务关掉（或已经是目标状态）时，它下面还没关的子任务按同样方式关掉，结果列在 `children` 里一并汇报，用户已关的子任务不动；`missing`／`deleted` 与推送同样处理。
- 周、月的「未完成」照旧只在周期结束后使用。

## 验收

- 只有确认写入的待办出现在滴答，且一条待办只对应一个滴答任务；重复推送不新建。
- 定时任务的开始、结束和全天标记已回读一致；缺时间保持全天，时段冲突不重复创建。
- 「滴答任务ID」回填后回读一致；滴答里已操作的状态由 Skill 同步到执行台，没有再让用户逐条确认；证据冲突的才问。
- 滴答里用户自己加的任务都被列出并给了建议。
- 长期任务的一步建成了主任务下的子任务，主任务的标题、日期、状态没变；子任务勾了主任务仍开着。
- 过期没勾的每条都给了去向；Agent 只改用户回过「行」的那几条，两边回读一致，没有新建重复任务。
- 调用失败、部分成功、找不到的任务都单列汇报，不说整体完成。

# 目标拆解

适用于做本月目标、安排这周、今天做什么。输入是执行台的现状、用户本次的说明和 [取证](sources.md) 的结果；产出是本周期的完整计划草案，用户确认后再写入。

## 333

- **月分两层**：九宫格每个维度最多 3 条月目标；其中「青蛙目标」（必须完成、重点盯的）全部维度合计最多 3 条，在月成果标题最前面加「🐸」。非青蛙目标也是月目标，同样写进执行台，不能因为青蛙名额满了就挪去待办工具。
- **周、日**：全部合计每周最多 3 个结果，每天最多 3 个待办。是否也分两层，用户还没确认，确认前按合计 3 项。
- 3 是上限，选 1–2 项也可以；不能把一堆事打包成「一项」来凑数。
- 已完成、取消的都留在本周期里，照样占名额（维度名额、青蛙名额都算）。名额满了还要加，必须说清楚挤掉哪一项、为什么，用户同意后才换；青蛙换人可以把原青蛙降成非青蛙，不必删掉。
- 不属于任何月目标的杂事放在用户原来的待办工具里，不在执行台另开一个待办池。

## 从年到日

1. **月**：读年度目标（目标、KR、当前行动、说明），结合用户本月最在意的现实问题，先按维度列全本月成果，再从中选最多 3 条青蛙。每项写清：月成果（可观察的结果）、完成标准、维度、关联年度目标、截止日期（落在本月内）、是否青蛙。找不到对应的年度目标就标「待确认」，不能硬挂。用户没提到的维度留空，不替用户补目标；但已知的本月大事（课程、交付、出差）要主动核对有没有漏列。
2. **周**：从周一到周日。选能推动月成果的里程碑，每项关联一条真实的月目标，写完成标准；跨月的周可以挂两个月的目标，但整周合计仍最多 3 项。
3. **日**：选今天能做完、能推动本周结果的最小交付，关联一条真实的周结果。用户没说今天有多少时间，就问一句，或者明说容量还没核实；不保证一定能完成。

成果要能验收：「整理资料」要收敛成「完成某份能直接用的清单，包含哪些项、经本人检查」。「努力、提升、坚持」这类词不能直接当完成标准，要先改写成本周期能看到的结果。

## 写入前校验

把执行台里同一周期的已有记录（历史迁入的除外）和本次新增、修改的合在一起，组成完整清单，通过 stdin 交给 `scripts/validate_plan.py`：

```json
{
  "level": "month",
  "period": "2026-10",
  "items": [
    {"title": "🐸示例成果", "dimension": ["工作事业"], "parent": "rec示例年度", "done_when": "示例标准", "due": "2026-10-31", "status": "未开始"}
  ]
}
```

- `level` 为 `month`、`week` 或 `day`。月的 `period` 写 `YYYY-MM`；周写该周周一的日期；日写当天日期。
- `parent` 填上级记录的 record_id。月目标的上级是年度目标，周结果的上级是月目标，待办的上级是周结果。
- 月、周的条目必须有 `done_when`；月的条目必须有 `dimension`（维度名或列表，跨维度的在每个维度都占名额），`due` 必须落在该月内；`title` 以「🐸」开头即青蛙。状态为「已完成」的月、周条目必须有 `actual_result`。
- 脚本只检查格式和数量，不证明上级记录真实存在，也不判断目标值不值得做；这两点要人工核对。示例数据不要写进用户的表。

校验通过后，按字段合同的「定位已有记录」先查后写：已有的更新，没有的新建；写完回读，核对数量、关联和状态。用户在飞书里手工填超过了名额（月：单维度超 3 条或青蛙超 3 条；周、日：超 3 项），就指出来并协助取舍，不删记录，也不能声称表格本身会限制条数。

## 看板与计划写入

v1.1 使用 BaseApp 数据绑定看板，未被用户取消。目标、状态或评分写入后，只回读执行台；看板筛选「是否本月」「是否本周」公式，周期自动切换。Agent 不生成目标文字、不刷新九宫格、不调用本地渲染脚本；实际建设状态和入口见私有配置与总控。

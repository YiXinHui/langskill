# 企业 AI 初诊入口工作流重构

## 变更背景

真实手测只激活 `lang-enterprise-ai-diagnosis` 后，首条回复仍然是：

> 可以。你先说说公司主要做什么，你平时直接负责哪些事情？

该行为来自当前产品规则与评测标准。旧入口把空激活直接映射为公司与职责采集；Eval 1、37 和 55 还持续奖励这一行为。后续 CaseV2 诊断结构已经存在，前台用户旅程没有独立建模，因此用户刚进入就感受到背景问卷，也不知道能够获得什么和可以从哪里开始。

## 入口体验结构

新增 `references/entry-experience.md`，建立前台入口体验：

```text
结果预期
→ 整体扫描／具体业务问题／已有 AI 想法
→ 对应业务入口
→ 既有 CaseV2 诊断主链
→ 初诊判断与下一步验证
```

空激活首轮先说明用户能够带走一份有边界的初诊判断和下一步验证建议，再用一个问题识别入口。首轮禁止直接询问公司做什么和用户负责什么，也禁止使用没有承接对象的“可以／好的／没问题”。

三种入口分别运行：

- 整体扫描先了解产品／服务和主要客户，再按需了解回答者职责；
- 具体业务问题先接住问题，只补一个会改变解释的工作或业务坐标；
- 已有 AI 想法保留方案原话，追到它准备改变的工作和业务结果。

用户首句已经提供业务、职责、问题、AI 想法、事件、恢复信息或结果请求时，直接旁路入口介绍，不要求重新选择或重讲。

## 对象与交互

`EnterpriseDiagnosisCaseV2` 增加 `entry_context`：

- `diagnosis_intent`：整体扫描、具体业务问题、已有 AI 想法或未明确；
- `entry_form`：空激活、只有意图、已有上下文或恢复会话；
- `route_source`：用户明确选择、上下文推断、系统激活或未知。

`DiagnosisStateV2.interaction.entry` 增加：

- `awaiting_intent | routed | bypassed`；
- `contract_presented`；
- 对 `case.entry_context` 的引用。

入口状态只保证前台方向感，不生成客户事实、候选优先级和 AI 判断。入口完成后不会重复产品介绍或三种选择。

## 渐进读取

空激活只读取 `entry-experience.md`。用户选择入口但尚未描述实际情况时继续使用入口分流。获得实质业务上下文后再读取诊断核心、CaseV2、StateV2 和后续对话协议。恢复会话直接读取已有案例与恢复点。

该调整减少首条回复前无效加载，并保留后续诊断所需的完整契约。

## 评测变化

- 重写 Eval 1、2、37、55 和 62，移除空激活直接采集公司与职责的旧奖励信号；
- 新增 Eval 80：整体扫描分流；
- 新增 Eval 81：具体业务问题分流；
- 新增 Eval 82：已有 AI 想法分流；
- 新增 Eval 83：首句带完整上下文时旁路入口；
- 新增 Eval 84：用户先询问最终产物；
- 新增 Eval 85：用户询问前台交流过程。

静态检查增加旧冷启动文案与旧评测标准扫描，防止后续版本重新出现同类入口。

## 兼容与范围

- CaseV2、StateV2、ResultV3、PresenterV2、HandoffV2 和 JudgmentProviderV1 保持现有版本；入口字段属于向后兼容的增加项；
- 旧状态恢复时使用 `entry_form: resumed`，没有证据时保持入口未指定；
- ResultV3 与 HandoffV2 不输出入口代码；
- 内部 Skill 和托管应用未纳入本轮修改。

## 验证

- 行为烟测：空激活、整体扫描、具体业务问题、已有 AI 想法、直接上下文、先问最终产物、询问交流过程共 7 个场景通过；直接上下文首次暴露的行业流程补造已修正规则并复测通过；
- 静态检查：596 项通过，覆盖 10 份运行时引用、85 个评测场景和三位老板公测门槛；
- 结构解析：11 份运行时文件中的 14 个 YAML／JSON 代码块通过解析；
- Skill 快速校验、共享目录校验、14 个公开 Skill 跨端安装测试、发布前敏感词扫描和 `git diff --check` 通过；
- Codex 与 Claude Code 的全局 Skill 入口均指向本仓库当前目录，无需重新安装。

行为记录见 `skills/lang-enterprise-ai-diagnosis/evals/2026-08-02_entry-workflow-v3_smoke-results.md`。

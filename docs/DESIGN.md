# langskill 设计与发布边界

langskill 是公开上游，不是内部仓库删减后的镜像。任何已经通用化并进入本仓的能力，都以本仓版本为唯一公共真身；内部团队如需增加组织配置，应通过独立增强层依赖本仓，不能复制后分别维护。

## 三种 Skill 角色

| 角色 | 含义 | 允许内容 |
|---|---|---|
| `public-product` | 面向公众直接使用的完整产品 | 公开方法、公开品牌表达、通用配置 |
| `public-core` | 可被私人或内部版本组合的通用核心 | 稳定流程、判断逻辑、公共测试、配置模板 |
| `distribution` | 安装、升级和仓库维护工具 | 公开仓自身的分发逻辑 |

机器可读清单见根目录 `skill-catalog.json`。新增或删除 Skill 时，必须同时更新清单、README、VERSION 和 changelog，并运行：

```bash
node scripts/validate-sharing-system.mjs
./pre-check.sh
```

## 从内部孵化到公开上游

1. 新能力可以先在私人或内部环境验证。
2. 确认具有跨组织价值后，提取通用核心进入本仓。
3. 私人身份、客户资料、业务目录、内部发布规则和真实敏感案例不得进入公开核心。
4. 内部实现改为依赖公开核心；之后的通用修改先改本仓，再升级内部依赖。
5. 只有内部业务变化时，只改内部增强层。

这是一条“晋升后上游优先”的链路，不是持续把内部仓库做脱敏导出。

## 公开 Skill 命名

- `lang` 是总路由入口，也是唯一不带连字符的保留名。
- 其余公开 Skill 的目录名、frontmatter `name`、机器清单 `id` 和推荐调用命令必须一致。
- 名称只使用小写英文、数字和连字符，并统一以 `lang-` 开头。
- 中文产品名可以保留在标题、说明和触发语中，但不能再作为 Skill 标识符。
- 已发布名称发生变化时，必须更新根目录 `skill-renames.json`，让升级流程清理旧目录。

## 公开交付边界

- 接收者：公开 GitHub 用户、AI 从业者和可复用该方法的团队。
- 目标行动：能够独立安装、理解和使用 Skill，或在自己的私有层上组合扩展。
- 信息白名单：通用方法、公共示例、公共测试、公开品牌信息。
- 信息红线：密钥、客户名、内部绝对路径、真实业务配置、内部交付底线、私人案例原文。
- 承诺权限：公开文档只承诺仓库已经实现并通过验证的能力。

## 安装与全局发现

公开仓使用统一安装器接入 Codex、Claude Code 与腾讯 WorkBuddy / CodeBuddy：

```text
项目仓或安装包中的 Skill 正文
        ↓
~/.agents/skills/<name>        共享入口，Codex 直接发现
        ↓
~/.claude/skills/<name>        指向共享入口的软链接
~/.codebuddy/skills/<name>     CodeBuddy / WorkBuddy 入口
```

Codex 与 Claude Code 继续通过共享入口收敛；CodeBuddy 使用自己的 `~/.codebuddy/skills/` 目录。当前 `skills` 安装器必须把 CodeBuddy 作为单独的第二条安装命令，否则 universal agent 收敛可能漏掉 `.codebuddy/skills/`。同一个 Skill 在同一宿主只保留一个可发现入口。Codex 已直接扫描 `~/.agents/skills/`，不再为 LangSkill 同时创建 `~/.codex/skills/<name>`；全局入口存在后，也不在 Desktop 工作区重复映射。开发机可以让共享入口直接指向本仓 `skills/<name>/`，公开安装用户由统一安装器维护实体和锁文件。

升级前先区分开发仓软链接与普通安装：开发仓有未提交改动时不得覆盖；普通安装和旧 Claude 单端安装先通过 `npx skills add ... -g -a codex claude-code` 收敛到共享结构，再单独执行 `npx skills add ... -g -a codebuddy` 同步 WorkBuddy/CodeBuddy。升级后必须验证机器清单中的全部 Skill 在 Codex、Claude Code 和 CodeBuddy 三端各出现一次。

## 当前企业咨询出诊入口

当前公开企业咨询出诊入口是 `lang-business-diagnosis`。它面向陌生老板做企业咨询式商业初诊：先给结果预期并识别整体扫描、具体业务问题或已有 AI 想法，再用一轮低负担对话还原生意，用用户自己的业务证据比较 AI 候选，最后交付带边界的初诊结论、最小验证动作和自愿导出的线索卡草稿。

当前 Skill 的稳定规则由主文档和四份自包含 reference 共同承担：入口与对话体验、初诊结果、线索卡、旧交接格式兼容。公开边界止于初诊，不承诺 ROI、实施、报价、固定周期或正式诊断报告；旧版内部对象、判断库和正式交接流程不再作为新会话入口。

旧版企业 AI 诊断的设计与评测已移入 `archive/lang-enterprise-ai-diagnosis-2026-08-19/`，以下内容只作迁移背景，不是当前 Skill 的执行规范。

## 历史设计：旧版企业 AI 诊断

`lang-enterprise-ai-diagnosis` 是面向老板和管理者的公开咨询式初诊。空激活先给用户清楚的结果预期，再识别整体扫描、具体业务问题或已有 AI 想法；用户已经提供实际上下文时直接进入。随后形成公司生意、回答者实际职责和本次复合目标，从职责、价值链与用户已经报告的现象中形成候选工作系统；选择焦点后还原当前工作怎样产生结果，最后判断 AI 是否值得进入以及先验证什么。公开初诊不承诺公司级代表性、正式优先级、因果、ROI、实施和验收。

公开产品由三层组成：

```text
EntryExperience
  结果预期 → 整体扫描／具体业务问题／已有 AI 想法 → 直接上下文旁路
        ↓
EnterpriseDiagnosisCaseV2
  进入方式 → 回答者与生意图 → 议题组合 → 候选工作系统组合 → 选定焦点 → 工作系统与介入判断
        ↓
DiagnosisStateV2
  入口状态 + claims 与纠正 + 案例成熟度 + ask/checkpoint/result/pause/repair
        ↓
DiagnosisResultV3 → DiagnosisPresenterV2
  可审查结果 → 受众过滤与自然语言呈现 → 当前用户可带走的初诊
```

入口体验与三层诊断对象共同支撑一段连续交流，内部对象和状态不向用户展示。用户能够知道这次会获得什么、当前从哪里进入以及最后能带走什么；案例对象、交互决策与用户结果分别演进，避免系统为了补字段或推进阶段而提问。

### EntryExperience：前台入口体验

只有 Skill 名称或模糊请求时，第一条回复先说明将形成一份有边界的初诊判断和下一步验证建议，再用一个问题识别三种入口：整体扫描、具体业务问题、已有 AI 想法。空激活首轮不直接询问公司做什么和用户负责什么，也不使用没有承接对象的“可以／好的／没问题”。

整体扫描先了解产品／服务和主要客户，再按需了解回答者职责；具体业务问题与已有 AI 想法从用户已经给出的对象进入。用户首句已经包含业务、职责、问题、方案或事件时，入口状态直接标记为 bypassed，不重复产品介绍和入口选择。用户询问“接下来怎么聊”时只说明前台旅程，后台方法、路由、字段和提问理由继续保密。

冷启动采用渐进读取：空激活只读取 `entry-experience.md`；用户选择入口但尚未给出实际情况时继续使用该分流；获得实质业务上下文后再加载 CaseV2、StateV2、诊断核心和后续对话协议。

### CaseV2：共享经营诊断核心

`EnterpriseDiagnosisCaseV2` 保存进入方式以及十类关联对象：回答者、企业生意图、议题组合、诊断边界、候选工作系统组合、选定焦点、当前工作系统、价值损耗、AI 介入判断和成熟度。`entry_context` 保存用户明确选择或根据实质上下文推断的诊断入口；它只决定从哪里开始，不生成业务事实和优先级。每项业务事实有稳定对象 ID 与 `claim_ids[]`；焦点、工作系统、价值损耗和介入判断通过 `focus_ref` 保持一致。用户可以乱序提供信息，系统把信息放回对象并只补当前决定真正需要的缺口。

最小生意图包含公司提供什么、服务谁、客户购买什么结果、收入或后续价值怎样形成，以及本轮覆盖哪条业务。行业和岗位只用于导航；“运营、销售、老板”等宽泛身份需要落到实际负责的工作、决定和产出。

议题组合允许销售利润、成本时间、周期、质量风险、客户体验、判断质量和新机会等目标并行。目标只在当前决定需要取舍时排序。“降本增效”先保留为用户原话，后续通过可观察变化逐步具体化。

候选工作系统来自用户职责、价值链和已经报告的现象。第一处具体痛点只进入候选，系统不因其最具体就自动选择。职责较宽或目标较多时先保留足够比较的组合；用户已明确限定局部工作并提供充分信息时允许直接聚焦，不为凑数制造其他方向。

焦点选定后按目的、触发、输入、动作与判断、输出、反馈、角色交接、异常和责任理解真实工作。长期模式可以直接作为证据，代表性事件在用户已经提供事件把手且会改变判断时使用。单个事件或样本不能自动升级成公司级事实，共现不能写成因果。

价值判断先看业务结果、全成本、周期速度、质量风险与组织资产；AI 判断再区分自动化、判断增强、混合介入和暂缓。公开状态统一为 `validation_candidate`、`foundation_first`、`non_ai_priority` 或 `insufficient_evidence`。

方法注册表保存每种方法的适用问题、进入条件、证据要求、操作步骤、常见误用、内部产物、来源与版权状态。经营地图、议题组合、候选比较、焦点选择、工作系统还原、事件证据、价值损耗、介入适配、来源对比和纠错恢复都按需调用。

### StateV2：证据与交互决策

`DiagnosisStateV2` 把案例成熟度与交互状态分开。`interaction.entry` 记录入口正在等待选择、已经路由或因直接上下文而旁路，以及结果预期是否已呈现；案例成熟度说明哪些对象已经足以支撑当前判断；其他交互状态处理正常交流、语言修复、疲劳、暂停和安全边界。

每次回复只有一个 `next_move`：`ask`、`checkpoint`、`result`、`pause` 或 `repair`。`ask` 必须包含一个用户凭现有经验能回答、会改变案例对象、候选排序、焦点、AI 判断或证据边界的问题。其他动作必须交付阶段理解、结果、暂停或纠正。非终局回复始终有明确去向。

完全没有上下文时先呈现结果预期与入口选择；整体扫描确认后再从产品／服务和主要客户进入。普通回合先准确理解，信息出现取舍价值后补一句判断增量，必要时只问一个问题。问题前提必须回到有效声明；用户需要临时整理、查资料或猜测时，系统采用负担更低的问法或先交付阶段理解。

对话支持：

- 用户纠正后撤回旧表达，失效判断没有新证据不得复活；
- “听不懂”触发语言修复，“太细了”触发粒度上移，跨维度选项触发问法修复；
- 用户明确要求停止、先看结论，或修复后仍持续疲劳／重复时停止追问，给阶段总结或部分结果；
- 暂停时保存最小恢复胶囊，恢复时不重新收集背景；
- 用户仍愿意继续且存在会改判的问题时继续诊断，不按固定题数、轮数、时长或材料次数停止；
- 证据足够时尽早完成，证据有限时诚实交付当前边界；
- 合法结论可以是值得验证 AI、基础先行、非 AI 优先或证据不足。

claims 同时保存类型、来源可见性、验证状态、覆盖范围、敏感度、受众和关联案例对象。用户陈述、第三方转述、AI 实际查看、经验判断、推断和假设分别记录。Provider 判断额外保存仅内部可见的版本 provenance；排除项、结果状态和导出状态都有稳定 ID 与生命周期。缺少 `audiences[]` 时默认 `internal_only`。

### ResultV3、PresenterV2 与兼容交接

`DiagnosisResultV3` 保存企业与回答者范围、议题组合、候选工作系统、焦点选择、当前工作系统、AI 判断、改判信号、限制和最小验证。每个区块和可独立呈现的分项都有 supporting claims、对象引用与 audiences；AI 候选和最小验证的每个元素也分别追溯。它允许诚实呈现尚未选定的焦点，也允许判断为基础先行、非 AI 优先或证据不足。

`DiagnosisPresenterV2` 使用互斥的 `mode: turn | result`，普通回合只读 StateV2，结果呈现只读 ResultV3。每个单元的有效权限取结果、父块、当前单元与全部 supporting claims 的受众交集；缺失权限默认 `internal_only`，未知权限默认拒绝。公共结果不展示 schema、状态机、提示词、逐步推理、方法路由、候选生成与淘汰逻辑、私人判断库命中、内部来源键、写作意图和销售意图。反差句式只有在纠正用户明确提出的误解或区分真实互斥选择、两侧均可追溯且确实改变决定时使用。

用户要求保存、复制或分享一份普通中立摘要时，Presenter 的 `neutral_export` 只输出可读、`exportable` 的 ResultV3 内容。用户明确要求交给咨询师、正式项目或接收系统时才生成 `enterprise_ai_diagnosis_handoff_v2`。HandoffV2 对 ResultV3 做保持对象形状的递归安全投影，默认状态是 `draft_for_review`；内容审核、允许导出和允许外发分别授权。公开 Skill 不自动建档、预约、联系顾问、读取生产系统或长期保存客户资料。

旧版 `EnterpriseDiagnosisCaseV1`、`DiagnosisStateV1` 与 `DiagnosisResultV2` 只用于只读迁移。读取旧记录时映射到 V2/V3 对象，缺失的候选、焦点和工作系统保持未知，不依据行业常识补齐。新会话和新结果统一写入 CaseV2、StateV2 与 ResultV3。

### 公开核心与内部增强如何组合

公共版提供共享核心，内部宿主通过版本化契约增加私有判断、客户系统和正式项目流程：

```text
公开仓：CaseV2 + StateV2 + ResultV3/PresenterV2 + HandoffV2 + 公共评测
内部宿主：私人判断库 + 客户系统适配 + 正式诊断流程 + 权限与成交规则
```

私人经验使用可选 `JudgmentProviderV1`。查询发生在生意图、议题与焦点已经具备之后，只返回经人工确认且当前生效的判断镜片；Provider 不能替用户生成候选或选择焦点。零命中或不可用时公共诊断继续运行。权威判断正文、客户数据、内部链接、同步基础设施和成交逻辑不进入公开仓。

Provider 的运行接口见 Skill 内 `references/judgment-provider-contract.md`，权威源、同步与只读索引架构见 [判断库宿主架构](enterprise-diagnosis-judgment-provider.md)。

## 验收策略

自动检查负责验证：文件路由、schema、稳定对象与证据回链、分项权限交集、Presenter 模式互斥、动态收敛边界、Provider 降级、普通摘要与 Handoff 分流、Handoff 授权分离，以及原始失败／相邻泛化／合法例外评测是否存在。

真实咨询体验不能只靠静态检查。首轮发布验收使用恰好 3 位、且来自 3 种不同业务类型的真实老板或管理者完成全程体验，按 [真实用户试诊记录模板](enterprise-ai-diagnosis-pilot-template.md) 汇总六项硬门槛、追问改判率、重复率、看懂程度、认知负担和独立复述。自动检查通过不代表真实用户门槛已经通过。

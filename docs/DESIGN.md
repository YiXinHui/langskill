# langskill 设计与发布边界

langskill 是公开上游，不是内部仓库删减后的镜像。任何已经通用化并进入本仓的能力，都以本仓版本为唯一公共真身；内部团队如需增加组织配置，应通过独立增强层依赖本仓，不能复制后分别维护。

## 三种 Skill 角色

| 角色 | 含义 | 允许内容 |
|---|---|---|
| `public-product` | 面向公众直接使用的完整产品 | 公开方法、公开品牌表达、通用配置 |
| `public-core` | 可被私人或内部版本组合的通用核心 | 稳定流程、判断逻辑、公共测试、配置模板 |
| `distribution` | 安装、升级和仓库维护工具 | 公开仓自身的分发逻辑 |

机器可读清单见根目录 `skill-catalog.json`。新增或删除 Skill 时，必须同时更新清单、README、VERSION 和 changelog，并运行：

```bash
node scripts/validate-sharing-system.mjs
./pre-check.sh
```

## 从内部孵化到公开上游

1. 新能力可以先在私人或内部环境验证。
2. 确认具有跨组织价值后，提取通用核心进入本仓。
3. 私人身份、客户资料、业务目录、内部发布规则和真实敏感案例不得进入公开核心。
4. 内部实现改为依赖公开核心；之后的通用修改先改本仓，再升级内部依赖。
5. 只有内部业务变化时，只改内部增强层。

这是一条“晋升后上游优先”的链路，不是持续把内部仓库做脱敏导出。

## 公开 Skill 命名

- `lang` 是总路由入口，也是唯一不带连字符的保留名。
- 其余公开 Skill 的目录名、frontmatter `name`、机器清单 `id` 和推荐调用命令必须一致。
- 名称只使用小写英文、数字和连字符，并统一以 `lang-` 开头。
- 中文产品名可以保留在标题、说明和触发语中，但不能再作为 Skill 标识符。
- 已发布名称发生变化时，必须更新根目录 `skill-renames.json`，让升级流程清理旧目录。

## 公开交付边界

- 接收者：公开 GitHub 用户、AI 从业者和可复用该方法的团队。
- 目标行动：能够独立安装、理解和使用 Skill，或在自己的私有层上组合扩展。
- 信息白名单：通用方法、公共示例、公共测试、公开品牌信息。
- 信息红线：密钥、客户名、内部绝对路径、真实业务配置、内部交付底线、私人案例原文。
- 承诺权限：公开文档只承诺仓库已经实现并通过验证的能力。

## 企业 AI 初诊与正式诊断的分层

`lang-enterprise-ai-diagnosis` 是面向公众的售前初诊产品，不是缩小版正式诊断。它默认最多追问 3 轮，把模糊的“想做 AI”收敛成老板能直接决策的三件事：现在最值得关注什么、要不要继续看 AI，以及值得时先看哪个具体工作画面。默认产物是一屏《企业 AI 初诊卡》：普通卡不超过 900 个非空白字符，低信息卡不超过 500 个，而不是必须先完成真实样本走查的八章报告。

冷启动第 0 轮使用“角色／工作范围选择 + 自由职责描述”的混合入口：老板／整体经营、销售／客户对接、交付／项目／生产、运营／行政／财务／人事、技术／数据／系统，以及其他。选择只决定后续用什么业务语言，不代表该范围存在问题；用户已经提供明确目标、痛点或近期事件时跳过角色入口。选择之后每轮只补一个业务坐标，继续受最多 3 个有效回答和绝对回合截止约束。

产品采用显式状态机，并同时记录有效回答与绝对用户回合。第三个有效回答或第四条用户消息先到时必须交付；累计两次低信息回答或用户要求停止时也立即交付。每回合最多要求用户完成一个动作；结果卡最多四个语义区块，面向用户的证据动作最多一个、也可以没有。L0 后只允许用户主动触发一次 L1 更新，更新后立即结束，不能靠“再补一包材料”无限深挖。

后台保留 L0／L1、来源类型、判断强度与更新边界；用户看到的卡片不用这些咨询术语，只说“现在怎么看、为什么这样判断、什么情况会换方向”。当结论是值得继续看 AI 时，必须用“谁 × 在什么时刻 × AI 改变什么动作 × 怎样看到反馈”描述一个候选工作画面；这不是试点计划。暂不进入或不建议做 AI 时不提供安慰性 AI 点子，也不把整改任务藏在结论里。

三层边界为：

- **L0 自述初诊**：一个回答者的业务描述与现象，后台形成主判断、另一种可能和换判断的信号；没有样本也必须能够完成。
- **L1 样本增强初诊**：相关证据可以是有数量、范围和结果的用户转述样本汇总（`sample_reported`），也可以是 AI 实际查看的脱敏材料（`sample_observed`）；两者都只在各自范围内更新判断，不能自动外推或识别因果。
- **L2 正式诊断**：跨角色、系统记录、真实操作、数据权限、ROI 和实施边界，由组织内部正式诊断承担。

普通事件、单次经验、“我有截图”或用户声称自己看过材料仍是 L0；只有合格汇总或 AI 实际读取材料才进入 L1。初诊卡可以建议“若要确认一个跨角色／ROI 问题，可另行进入正式诊断”，但不会自动生成、发送或写入交接；用户看完结果并明确要求后，才单独生成 `draft_for_review` 草稿。

公开初诊不读取客户系统、不保存销售线索，也不把用户自述升级为正式客户事实。组织内部的正式诊断流程负责核验真实操作、跨角色分歧、数据与权限、候选优先级和实施边界。两层通过交接契约衔接，不共享客户配置、内部策略或成交逻辑。

判断库不再属于公开初诊默认运行链。未来具体应用如需注入私有判断，只能作为宿主扩展，并遵循 [判断库扩展设计](enterprise-diagnosis-judgment-provider.md)；索引、同步、过期与降级等基础设施不得进入普通对话，也不能替客户事实或真实样本背书。

当前评测除保留单回合防回退外，主要看端到端完成：首次有用判断出现在哪一轮、绝对回合截止是否生效、是否重复提问、纠正能否保持、L1 是否只更新一次、结果是否使用老板语言、AI 候选是否是具体工作画面而非实施链，以及是否敢给出“暂不做 AI”。方法研究依据包括 CDC 对问题理解／回忆／判断／作答负担的认知访谈框架、美国 Census 对目标回答者预试的要求，以及 GOV.UK 对问题用途、条件分支和端到端完成率的服务评测原则。
